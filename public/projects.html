01 / 06 Foundation

Multi-Agent AI Platform

One governed foundation on Google Cloud that gives specialist AI agents shared sign-in, data-tier separation, central model management, audit logging and a tested, region-only deploy path.

Problem

Consulting and operations work (change programs, license reviews, infrastructure health checks, security reviews) was done by hand, and quality varied from one practitioner to the next. Each AI experiment had to solve sign-in, data separation, model choice, audit and deployment again from scratch. On top of that, a strict organization policy banned multi-region cloud resources, which broke the default container registry and build path.

What it does

It hosts many specialist AI agents behind one serverless backend on Google Cloud Run. Each agent is its own module (a FastAPI "router") inside one shared Python service. The browser reaches it through Firebase Hosting, which forwards API calls to the backend, so web pages never hold a backend address. Agents draw on shared building blocks:

  • Google sign-in, verified on the server.
  • One allowlist of who may use the platform, which denies access if it can't be read.
  • Two data-access tiers on the agents wired to them: real customer data only for verified users on an allowed domain, and a synthetic sample dataset for everyone else.
  • A central registry that sets each agent's AI model. Admins can change it at runtime, and it blocks models served outside approved regions.
  • A weekly model-lifecycle steward that keeps agents off retired models.
  • A tracked background-job pattern for long analyses.
  • A one-command, region-only deploy with a test gate and quick rollback.

An opt-in governance framework (kill switch, tamper-evident audit trail, shared rate limits, reversible masking of customer identifiers, and autonomy rules) was built from composable building blocks. It was first adopted by the agent that handles the most sensitive data.

Value

Building a new agent mostly means writing its domain logic, because sign-in, admission control, model management, audit logging and a tested deploy path are already there to plug into. Admins see a countdown before a model they rely on is retired. If a registry-managed agent's model disappears, the next weekly run moves it to a same-tier replacement. The serverless runtime scales to zero when idle, builds stay in approved regions, and admins can only pick models served in those regions.

Built on this foundation

The next three projects on this page run on this platform. Each one is its own module in the shared backend, so it starts with the platform's sign-in, central model registry and one-command deploy path, and adds its own domain logic. What each one takes from the platform:

Change Management (OCM) Agent ↓Its own router on the shared backend, sign-in through the platform, models from the central registry, and project deletion limited to verified platform admins. License Right-Sizing Agent ↓The allowlist and data-access tiers, a per-agent admin role, central model selection, and the Cloud Run Jobs worker pattern for long runs. Infra Health Check Agent ↓The allowlist and data-access tiers, the untrusted-input pipeline, the platform rate limiter, registry-managed models for its chat, and the async job pattern.

FlowHow a request moves through it

  1. 1Step 1: A user opens the site on Firebase Hosting. Allowed-domain users sign in with Google. Other allowlisted users are admitted to the restricted tier, which sees only synthetic sample data.
  2. 2Step 2: Agent pages call relative API paths with the sign-in token attached. Hosting forwards those calls to the FastAPI service on Cloud Run.
  3. 3Step 3: On routes that require authentication, a shared check verifies the token, checks the allowlist (denying access if the lookup fails), and works out the data tier and admin rights.
  4. 4Step 4: The request reaches the agent's router. The infrastructure report analyzers send uploaded text through the sanitize, redact, injection-flag and wrap pipeline. The governed agent also runs its guard: the policy check (kill switch, autonomy rule table, decision log), then the access check, then the shared rate limit.
  5. 5Step 5: Registry-managed agents get their model from the central registry, and Gemini on Vertex AI does the inference. Instrumented agents write token and cost records to the usage ledger.
  6. 6Step 6: Short work returns directly. Long work creates a job record and returns its ID. For the longest-running agents a Cloud Run Job built from the same image does the work, and other agents use a background thread. The UI polls until the result is stored.
  7. 7Step 7: Results are saved in Firestore. On tier-wired agents they are tagged with tenant and data class, and read paths and totals are filtered by the caller's tier. Audit events go to Cloud Logging, and the governed agent also seals them into its tamper-evident chain.
  8. 8Step 8: Every week a scheduler calls a key-protected endpoint. The model-lifecycle steward test-calls each model, switches agents only off models that return not-found, applies same-tier upgrades that passed a test call, and records recommendations, blocked successors and a retirement countdown for admins.
  9. 9Step 9: Changes ship through one deploy command: test gate, regional build, service and worker deploy, then a health check. A separate authenticated smoke test can verify the result, and revision rollback is the escape hatch.

Change Management (OCM) Agent

Turns a formal four-phase change-management methodology into software: each deliverable is generated from a versioned methodology document and stamped with the version that produced it.

Problem

Change-management deliverables, such as stakeholder matrices, impact assessments, and communication and training plans, take a senior consultant weeks to produce, and quality depends on who writes them. Generic AI chat produces generic content, invents stakeholders and figures, and can't show which methodology it followed.

What it does

A consultant creates an engagement and picks capabilities from a configurable feature library. AI can suggest features, but only from that catalog. Uploaded source documents are extracted and summarized into structured context. The agent then writes a discovery interview tailored to the chosen features, pre-filling answers the documents already contain. The interview can be answered in the web app, or exported as a Word worksheet, taken to the customer and uploaded back. Each deliverable is then generated with the full methodology (a human-editable "skill" document) sent ahead of every prompt. That document requires a fixed output structure: which phase and deliverable this is, whether prerequisites are met, four execution tasks with any gaps listed, the model's own quality-gate checks, and practitioner notes. Finally, the agent combines everything into one change plan and exports branded PDF and editable Word documents. The methodology covers 4 phases and 18 standard deliverables.

Value

Every run works from the same methodology, so deliverable sets are consistent. Each deliverable record carries the methodology version: the declared version plus a fingerprint of the document's exact text. The model is told to flag missing information as a gap instead of inventing it, and gaps and gate results are shown for human review. Methodology owners change the practice by editing a document, with no code change, and the next deploy picks it up. A multi-week deliverable process becomes consistent, exportable output on demand.

FlowHow a request moves through it

  1. 1Step 1: The consultant signs in through the platform and creates an engagement in a 3-step wizard: details and change type, features from the library and/or custom modules, then review.
  2. 2Step 2: Optionally, the AI recommends a feature set based on the description, documents and interview. Suggestions not in the catalog are discarded, and the consultant accepts or edits the rest.
  3. 3Step 3: The consultant uploads source documents. Text is extracted (pages and tables), summarized into structured context and stored with the engagement.
  4. 4Step 4: The agent generates a discovery interview scoped to the selected features, pre-filling answers the documents already contain. The consultant answers in the app, or downloads the Word worksheet, runs the customer interview offline and uploads it, and answers are mapped back by question ID.
  5. 5Step 5: For each feature, the deliverable generator starts the prompt with the versioned methodology document and asks for the fixed structure. The model is told to mark tasks that lack context as pending and list the gaps rather than invent content.
  6. 6Step 6: Each deliverable is saved with the methodology version (declared version plus content fingerprint) and the phase and standard deliverable ID from the model's classification.
  7. 7Step 7: The plan synthesizer combines all deliverables and interview answers into one change plan for the sponsor.
  8. 8Step 8: The consultant reviews gate results, listed gaps and practitioner notes, then exports the full pack as a branded PDF or editable Word document. Practice chat can answer questions across the practice's engagements.

License Right-Sizing Agent

Per-user Google Workspace license-tier recommendations built from actual usage, where fixed rules make the decision and AI only advises.

Problem

License optimization usually comes down to a spreadsheet and a guess. Native admin views show who holds a seat, not whether the seat fits how that person works. A naive "low usage means downgrade" rule wrongly penalizes people who are active but quiet, or whose work happens where Google's per-user reporting is thin, such as editing in Docs, Sheets and Slides. That makes right-sizing recommendations hard to defend.

What it does

It reads an organization's actual Google Workspace data through delegated access and only ever lists data, never changes it. That data covers:

  • directory state
  • per-app usage, swept day by day across the full lookback period
  • audit-log activity for Chat, Meet, Calendar and Gemini
  • current base and add-on license assignments

It builds one profile per user and scores each profile in one of two modes. Fast mode uses fixed rules only. Deep mode adds a per-user Gemini recommendation. Every result then passes through a rule-based decision layer that:

  • only recommends within the user's confirmed license family
  • never recommends a license that can no longer be bought
  • refuses to downgrade an active account that has no measurable usage evidence

Recommendations go to a reviewer console with a status workflow and can be exported as PDF, Word or CSV.

Value

It builds a right-sizing case where every per-user verdict can be traced to the usage signals behind it. When evidence is thin, the honest outcome is "insufficient data" rather than a guess. Active-but-quiet users and admins are protected from automatic downgrades by design. The agent recommends tiers, not dollar figures, and never computes or estimates prices.

FlowHow a request moves through it

Infra Health Check Agent

Turns raw multi-site infrastructure health-check exports into structured, severity-labeled findings, issues tracked across runs, and reports ready to share.

Problem

Routine health checks across multi-site hyperconverged infrastructure (servers where compute and storage are combined) produce large raw JSON exports from automated check scripts, one per site, host or scan. Engineers read them by hand, so issues get skimmed or missed. A problem that keeps coming back looks new each time, and turning the output into a stakeholder report is manual work repeated every cycle.

What it does

Engineers drop one or more health-check exports into a web console. The payload first goes through an input-safety pipeline that caps size, strips stray control characters, redacts known secret and sensitive-data patterns and flags likely prompt injection. A large-context Gemini model then analyzes it in a background job. The model is told today's date, instructed to list every issue in every file section, and given a summary of the previous run for comparison. It returns structured results: overall status; findings with severity, component, site, issue, recommendation and impact; automation opportunities; alert-reliability concerns; and trend. Critical and high findings become tracked issues, merged by component across runs. Results feed a dashboard, PDF and Word reports, and a chat that answers questions across recent runs.

Value

Health findings with recommended fixes in the same structure on every run. A component's recurring problems build up an occurrence history instead of looking new each time. A coverage record shows which uploaded file sections fell within the input sent to the model, and any truncation is disclosed rather than hidden. Reports come out ready to share, with no manual write-up.

FlowHow a request moves through it

  1. 1Step 1: An engineer drops one or more health-check JSON exports into the console. The browser joins them, adds a header for each file and compresses the payload.
  2. 2Step 2: The API checks the user against the allowlist, applies the per-user upload rate limit and decompresses the payload.
  3. 3Step 3: The input-safety pipeline caps size, strips control characters, redacts known secret and sensitive-data patterns, flags suspected prompt injection, and writes an audit event if anything is caught.
  4. 4Step 4: The API creates a job record and returns its ID immediately. A background worker picks up the analysis.
  5. 5Step 5: The worker loads a summary of the most recent run and sends the redacted input to Gemini, capped to the context budget. The request includes today's date, the instruction to list every issue, the environment notes and the required output structure.
  6. 6Step 6: The response is parsed (and recovered if needed), and a coverage record of which file sections fell within the model input is attached.
  7. 7Step 7: The run is stored with a capped, redacted excerpt of the raw input. Critical and high findings are added to the issue tracker or merged into existing issues by component.
  8. 8Step 8: The browser polls until the job completes. The dashboard then shows overall status, severity counts, the trend across recent runs and the top open issues.
  9. 9Step 9: Engineers triage issues (acknowledge, resolve, assign, add notes) and download the PDF or Word report.
  10. 10Step 10: The agent chat answers questions across recent runs and cites the run IDs it draws on.

RevokAI — Governed Access Control

A governed AI compliance control for access revocation: AI correlates, rules and a human decide, and every action is evidenced.

Problem

Access-revocation compliance controls rely on manual analysis. The hardest step is matching people who have left to the accounts they still hold, because the identifiers often sit in metadata and free text where a standard report can't join them. That matching is slow human work, and the control costs roughly 25 hours a week to run manually.

What it does

RevokAI turns the manual control into a closed loop with five stages: detect, validate, approve, remediate, prove. An AI agent matches leavers to accounts even where the match is buried in metadata or free text. Fixed rules apply the revocation deadline (SLA), and each exception ends up in a named outcome. A human approves every remediation action. Every action is ticketed and timestamped, and each run produces an audit trail that can be exported. I co-built RevokAI in a sponsored squad, contributing the agent workflow and its run outputs.

Value

It moves an access-revocation control from a weekly manual grind to an on-demand run that takes minutes and produces its own audit trail. It targets the roughly 25 hours a week (about 1,300 hours a year) that the control costs to run manually today. That figure is the current manual cost, not a measured saving. The same pattern (AI reasons, fixed rules decide, humans approve the action) carries over to other controls such as access recertification.

FlowHow a request moves through it

  1. 1Step 1: Detect: the loop takes in leaver records and the account data to check them against.
  2. 2Step 2: Validate (AI): the matching agent links leavers to accounts where identifiers are buried in metadata or free text.
  3. 3Step 3: Validate (rules): fixed rules apply the revocation deadline.
  4. 4Step 4: Validate (outcome): each exception lands in a named outcome: breach, within SLA, compliant, or for review.
  5. 5Step 5: Approve: a human reviews each proposed remediation. Nothing goes ahead without approval.
  6. 6Step 6: Remediate: each approved action is raised as a remediation ticket.
  7. 7Step 7: Prove: every action is ticketed and timestamped, and the run is compiled into an audit trail that can be exported as control evidence.

Customer Outreach Agent

Evidence-gated customer outreach: research, score, then draft, with a human reviewing every message.

Problem

Researching an account properly before reaching out takes hours per customer. You have to work out its current strategic priorities and which services actually fit them. Without that research, outreach at scale turns into generic, low-relevance messages.

What it does

For each target account, the agent researches the customer's current strategic priorities using real-time web search, maps them to a service portfolio, and scores the fit out of 100. Only opportunities scoring 80 or above go on to drafting. For those, the agent writes personalized outreach grounded in the customer's actual goals, and a human reviews every draft before anything reaches a customer. Research, scoring and drafting run end to end from a single command. I designed and built it.

Value

It replaces hours of manual research per account with one command. Each message rests on current research into that customer rather than a template. Because of the 80/100 evidence gate, no draft is written unless the research supports the opportunity.
