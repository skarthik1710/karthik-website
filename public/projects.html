01 / 16 Built Google Cloud

Google Workspace agent platform

A governed platform for AI agents that work on Google Workspace data, where agents never hold the credentials and never see real identities.

My role

Built it end to end: portal, tool servers, policies, release tooling and security checks.

Problem

AI agents that analyse an organisation's Google Workspace (licences, security settings, reseller subscriptions, support tickets) need very powerful admin-level read access. Giving that access to each agent, with weak sign-in and no audit trail, is a risk no security team accepts.

What it does

A shared platform that the agents run on. Users sign in through one portal; an access list decides who may use each agent and who may see real data. All Workspace access goes through a single read-only tool server that holds the only credential, checks a policy before every read, and replaces people's identities with keyed pseudonyms before any agent or model sees the data. A second tool gives read-only ticket access, and a third chooses and automatically re-qualifies the Gemini model each agent uses. Changes reach the release environment only through one scripted promotion that reuses the exact tested images and runs a security check suite before and after.

Value

The powerful credential lives in one small, auditable place. Agents can be added without widening access. Every read is logged in a tamper-evident trail. Releases are repeatable and reversible.

02 / 16 Led and built Kubernetes

Agent platform foundation

A secure-by-default foundation for shipping governed AI agents on enterprise Kubernetes.

My role

Led and built it; the platform operators added image signing on top.

Problem

Teams that want to put AI agents on a shared enterprise Kubernetes platform face the same hurdles each time: proving who is calling an agent, deciding what each agent and each tool is allowed to do, keeping secrets and unpinned dependencies out of the build, and meeting the platform's rules for images and deployment. Solved one agent at a time, these controls drift, and a single gap at the trust boundary can let a caller claim permissions they do not have.

What it does

A reusable foundation that every agent starts from. It contains a small reference agent that exercises the whole path end to end, a shared identity module that verifies each caller's signed token, a policy layout in which Open Policy Agent decides on every request and every tool call, and a suite of automated "contract" tests that hold every project to the same rules. A delivery pipeline tests, scans and builds container images, and a read-only health check tells a developer whether the platform's model gateway, tracing and tool gateway are reachable and whether their keys work. New agents are created by copying the reference agent and renaming it.

Value

New agents inherit identity, authorisation, secret handling and supply-chain controls instead of re-implementing them. Rules are enforced by tests in the pipeline, not by convention. Each agent stays independent (own policy, prompt, tests, image), so teams can change and release them separately. Framework upgrades arrive as a tested, reviewable change.

03 / 16 Built Microsoft Entra ID · ServiceNow

Directory group membership agent

An access-request agent that reads a ServiceNow ticket, lets rules or a named approver decide, changes the directory group through Microsoft Graph and proves the change before closing the ticket.

My role

Built it: design, workflow engine, integrations, approval rules, chat and request pages, tests.

Problem

Requests to add or remove someone from a directory security group arrive as free text and are worked by hand. Automating them is risky if an AI is allowed to decide who gets access.

What it does

Requests come from a chat page or a ServiceNow catalog item. A language model only turns the text into a structured request. Code checks the requester, the group and the user against an allowlist of directory object IDs, then approval rules decide: approve automatically, route to a named approver in ServiceNow, or decline. After approval the request is checked again, the membership is changed through Microsoft Graph, read back from Microsoft Entra ID to confirm, recorded in an audit log, and the ticket is closed with notes at every step.

Value

Shows how routine access tickets can be completed end to end while the approval decision stays with written rules or a person, with a full record of who asked, who or what approved, and what actually changed.

04 / 16 Built Azure · AWS

Outage response agent

An operations agent that works an outage from both ends: it responds when a server goes down, and it is designed to flag trouble before the server becomes unavailable.

My role

Built it: agent, rules, roster and notification tools, cloud trigger and restart path.

Problem

"Server unreachable" tickets arrive around the clock. Some are false alarms, yet each can pull an on-call engineer out of bed, and a real outage is only noticed after the service is already down. Operations teams need false alarms filtered out, real outages handled fast, and early warning before a failure.

What it does

The agent has two modes that share the same rules, policy checks, duty roster and notification tools. Reactive: when a server stops, a ticket is raised in ServiceNow and the agent picks it up, validates the server, and fixed rules sort the result into false alarm or outage. For an outage it looks up who is on duty and phones that engineer, escalating to the next person if nobody responds. On the call the engineer can press a key to restart the server; the agent then restarts it, re-checks it, resolves the ticket and calls back to confirm. Proactive: the agent is designed to watch the server's health signals, identify a potential issue and flag it to the on-duty engineer before the server becomes unavailable, using the same roster, call and ticket path.

Value

Designed to cut unnecessary after-hours callouts, shorten the time from failure to restart, and move the first warning ahead of the outage. Every default leans towards calling a person when in doubt.

FlowReactive: when a server goes down

  1. 1Step 1: A server stops and a ticket is raised in ServiceNow.
  2. 2Step 2: The agent receives the ticket and validates the server.
  3. 3Step 3: Rules classify the result; anything unclear is treated as an outage.
  4. 4Step 4: False alarm: note added, priority lowered, routed for daytime review; nobody is called.
  5. 5Step 5: Outage: the roster returns who is on duty; the agent sends an SMS and places a call.
  6. 6Step 6: No response within the time limit: the next person, then a fallback group.
  7. 7Step 7: On the call the engineer presses a key to restart; the agent starts the server, waits for health checks, resolves the ticket and confirms by phone.

  2. P2Step P2: It identifies a potential issue before the server is unavailable.

RevokAI — Governed Access Control

A governed AI compliance control for access revocation: AI correlates, rules and a human decide, and every action is evidenced.

Problem

Access-revocation compliance controls rely on manual analysis. The hardest step is matching people who have left to the accounts they still hold, because the identifiers often sit in metadata and free text where a standard report can't join them. That matching is slow human work, and the control costs roughly 25 hours a week to run manually.

What it does

RevokAI turns the manual control into a closed loop with five stages: detect, validate, approve, remediate, prove. An AI agent matches leavers to accounts even where the match is buried in metadata or free text. Fixed rules apply the revocation deadline (SLA), and each exception ends up in a named outcome. A human approves every remediation action. Every action is ticketed and timestamped, and each run produces an audit trail that can be exported. I co-built RevokAI in a sponsored squad, contributing the agent workflow and its run outputs.

Value

It is designed to turn an access-revocation control from a weekly manual grind into an on-demand run that takes minutes and produces its own audit trail. It targets the roughly 25 hours a week (about 1,300 hours a year) that the control costs to run manually today. That figure is the current manual cost, not a measured saving. The same pattern (AI reasons, fixed rules decide, humans approve the action) carries over to other controls such as access recertification.

Infra Health Check Agent

Turns raw multi-site infrastructure health-check exports into structured, severity-labeled findings, issues tracked across runs, and reports ready to share.

Problem

Routine health checks across multi-site hyperconverged infrastructure (servers where compute and storage are combined) produce large raw JSON exports from automated check scripts, one per site, host or scan. Engineers read them by hand, so issues get skimmed or missed. A problem that keeps coming back looks new each time, and turning the output into a stakeholder report is manual work repeated every cycle.

What it does

Engineers drop one or more health-check exports into a web console. The payload first goes through an input-safety pipeline that caps size, strips stray control characters, redacts known secret and sensitive-data patterns and flags likely prompt injection. A large-context Gemini model then analyzes it in a background job. The model is told today's date, instructed to list every issue in every file section, and given a summary of the previous run for comparison. It returns structured results: overall status; findings with severity, component, site, issue, recommendation and impact; automation opportunities; alert-reliability concerns; and trend. Critical and high findings become tracked issues, merged by component across runs. Results feed a dashboard, PDF and Word reports, and a chat that answers questions across recent runs. I built it on the first-generation platform.

Value

Health findings with recommended fixes in the same structure on every run. A component's recurring problems build up an occurrence history instead of looking new each time. A coverage record shows which uploaded file sections fell within the input sent to the model, and any truncation is disclosed rather than hidden. Reports come out ready to share, with no manual write-up.
