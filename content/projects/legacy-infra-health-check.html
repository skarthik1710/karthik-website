Infra Health Check Agent

Turns raw multi-site infrastructure health-check exports into structured, severity-labeled findings, issues tracked across runs, and reports ready to share.

Problem

Routine health checks across multi-site hyperconverged infrastructure (servers where compute and storage are combined) produce large raw JSON exports from automated check scripts, one per site, host or scan. Engineers read them by hand, so issues get skimmed or missed. A problem that keeps coming back looks new each time, and turning the output into a stakeholder report is manual work repeated every cycle.

What it does

Engineers drop one or more health-check exports into a web console. The payload first goes through an input-safety pipeline that caps size, strips stray control characters, redacts known secret and sensitive-data patterns and flags likely prompt injection. A large-context Gemini model then analyzes it in a background job. The model is told today's date, instructed to list every issue in every file section, and given a summary of the previous run for comparison. It returns structured results: overall status; findings with severity, component, site, issue, recommendation and impact; automation opportunities; alert-reliability concerns; and trend. Critical and high findings become tracked issues, merged by component across runs. Results feed a dashboard, PDF and Word reports, and a chat that answers questions across recent runs. I built it on the first-generation platform.

Value

Health findings with recommended fixes in the same structure on every run. A component's recurring problems build up an occurrence history instead of looking new each time. A coverage record shows which uploaded file sections fell within the input sent to the model, and any truncation is disclosed rather than hidden. Reports come out ready to share, with no manual write-up.

FlowHow a request moves through it

  1. 1Step 1: An engineer drops one or more health-check JSON exports into the console. The browser joins them, adds a header for each file and compresses the payload.
  2. 2Step 2: The API checks the user against the allowlist, applies the per-user upload rate limit and decompresses the payload.
  3. 3Step 3: The input-safety pipeline caps size, strips control characters, redacts known secret and sensitive-data patterns, flags suspected prompt injection, and writes an audit event if anything is caught.
  4. 4Step 4: The API creates a job record and returns its ID immediately. A background worker picks up the analysis.
  5. 5Step 5: The worker loads a summary of the most recent run and sends the redacted input to Gemini, capped to the context budget. The request includes today's date, the instruction to list every issue, the environment notes and the required output structure.
  6. 6Step 6: The response is parsed (and recovered if needed), and a coverage record of which file sections fell within the model input is attached.
  7. 7Step 7: The run is stored with a capped, redacted excerpt of the raw input. Critical and high findings are added to the issue tracker or merged into existing issues by component.
  8. 8Step 8: The browser polls until the job completes. The dashboard then shows overall status, severity counts, the trend across recent runs and the top open issues.
  9. 9Step 9: Engineers triage issues (acknowledge, resolve, assign, add notes) and download the PDF or Word report.
  10. 10Step 10: The agent chat answers questions across recent runs and cites the run IDs it draws on.

Health-check console

Multi-file upload with in-browser compression and progress. The dashboard shows overall status, severity counts, the trend across recent runs and top open issues. The console also offers issue triage, run history, report downloads, a one-off analyzer that doesn't store results, and an agent chat tab.

Sign-in and access-control allowlist

03 Input safety

Secure input pipeline

One entry point for all uploaded text. It enforces size caps, strips null bytes and control characters, and redacts known secret and sensitive-data patterns: API keys and tokens, password and secret fields, and card-number and US Social Security number formats. It also flags likely prompt injection, and anything flagged is written to the audit log.

05 Reasoning

Health analysis engine

A single large-context analysis sized to the model's context window. The prompt includes today's date so historical timestamps aren't flagged as clock problems. The model is told to list every issue in every file section and compare against the previous run, and it returns structured JSON at low temperature.

Coverage record

Labels each uploaded file section as fully inside, partly inside or outside the input sent to the model. Truncation is recorded in the run and shown in reports, and the model is told to mention it in its summary.

Run store

Saves each run's analysis, severity counts, coverage record and a size-capped, secret-redacted excerpt of the raw input.

Issue tracker

Turns critical and high findings into tracked issues. A new finding on a component that already has an open issue updates that issue (occurrence count, last seen) instead of creating a duplicate. People triage issues by status, assignee and notes. Deleting a run removes only the issues seen in that run alone.

Report generator

Human in the loop

Engineers decide what to analyze by uploading the health-check exports. They triage every tracked issue (acknowledge, resolve, assign, add notes) and own all remediation. The agent never connects to or changes infrastructure; it only reads the exports it is given. It recommends fixes and automation opportunities, and people decide what to act on. Deleting a run and its history is limited to admins.
